# Универсальные формы и админка схем

Требования: CORE-1…CORE-9, DATA-1…DATA-3, NFR-1. Сценарии: C-01…C-04, N-11.

## 4.1 Универсальный список — `/entities/{type}`
Один шаблон для любого типа (partner, service, signature, qos_profile, duration, protocol, subscriber, qos_assignment, offer и любых новых).
```text
QoS-профили                                                   [+ Создать]
┌────────┬──────────┬─────────┬──────────┬─────────┬──────────┬──────────┐
│ Код    │ Название │ Мбит/с  │ Приоритет│ Множ.   │ SLA, %   │          │
├────────┼──────────┼─────────┼──────────┼─────────┼──────────┼──────────┤
│ BRONZE │ Bronze   │ 10      │ 1        │ 1.0     │ 99.0     │ [✎] [🗑] │
│ GOLD   │ Gold     │ 50      │ 3        │ 2.0     │ 99.9     │ [✎] [🗑] │
│ …      │          │         │          │         │          │          │
└────────┴──────────┴─────────┴──────────┴─────────┴──────────┴──────────┘
```
- Колонки — свойства схемы типа в порядке объявления, подписи — `title` из схемы.
- Меню слева — список типов из `GET /api/v1/schemas`; новый тип появляется там сам.
- Удаление записи с детьми: «Будут удалены связанные записи: N» (по `relations.json`) → `[Удалить]`.

## 4.2 Универсальная форма
Строится по схеме (`SPEC.md` §7, «Рендерер форм»):
```text
Новая сигнатура
Сервис*        [Link ВКС ▼]        ← поле x-ref на service (подпись — name)
IPv4*          [____________]
IPv6           [____________]      ← появится после правки схемы (C-02)
URI            [____________]      ← необязательно после правки (C-02)
Порт*          [_____]  1…65535
Протокол*      [HTTPS ▼]           ← список из справочника protocol
               [Сохранить]  [Отмена]
```
- Типы полей: текст, число (`min`/`max`), выбор (`enum` или `x-ref`), флажок. Остальные ключевые слова схемы не отображаются, но проверяются сервером.
- Ошибки сервера (422) выводятся под соответствующим полем теми же текстами, что и в API (CORE-6).

## 4.3 Админка схем — `/admin/schemas`
```text
Схемы сущностей                         [Перечитать конфиг]    [+ Новый тип]
┌ Типы ───────────┐ ┌ signature · «Сигнатура» ─────────────────────────────┐
│ partner         │ │ {                                                    │
│ service         │ │   "title": "Сигнатура",                              │
│ ▸ signature     │ │   "type": "object",                                  │
│ qos_profile     │ │   "properties": {                                    │
│ duration        │ │     "ipv4": {"type":"string","format":"ipv4",…},     │
│ protocol        │ │     …                                                │
│ subscriber      │ │   },                                                 │
│ qos_assignment  │ │   "required": ["service_ref","ipv4","port",…]        │
│ offer           │ │ }                                                    │
└─────────────────┘ └──────────────────────────────────────────────────────┘
 [Сохранить схему]  [Сбросить к сохранённой]     Записей этого типа: 5
```
Поведение:
- `[Сохранить схему]` → `PUT /api/v1/schemas/{type}`; успех — `✓ Схема сохранена. Формы обновятся после перезагрузки страницы`.
- Невалидная схема (например, `{"properties": "not-an-object"}`) → `⚠ Схема некорректна: properties должен быть объектом`, прежняя версия остаётся (CORE-2).
- Нарушение наших расширений (`x-ref` на несуществующий тип) → `⚠ x-ref ссылается на неизвестный тип: …`.
- `[+ Новый тип]` — диалог: идентификатор типа (латиница), название, начальная схема (шаблон `{type: object, properties: {}}`) → тип создаётся и сразу появляется в меню и в `/entities/{type}` (CORE-7, пример «Мониторинг»).
- Если у типа уже есть записи, при удалении поля показывается: «Записей с этим полем: N; они останутся, поле перестанет отображаться».
- `[Перечитать конфиг]` → `POST /admin/config/reload` для YAML (`process`, `pricing`, `px_payload`, `mock_rules`, `protocols`). Ошибка формата: `⚠ pricing.yaml: строка 4: …`, прежний конфиг сохранён.

## 4.4 Как выглядит «до и после» (для сценариев «поменяйте вот это»)
| Правка схемы | Форма до | Форма после |
|---|---|---|
| `signature`: добавить `ipv6`, убрать `uri` из `required` | IPv4*, URI*, Порт*, Протокол* | IPv4*, IPv6, URI, Порт*, Протокол* |
| `service`: добавить `sla_percent` (99–99.999) | Название*, Описание | + «SLA, %» с диапазоном; 50 → `⚠ Значение должно быть не меньше 99` |
| новый тип `monitoring` | раздела нет | в меню «Мониторинг»: Endpoint*, Интервал, сек (≥ 10), Сервис* |
Старые записи после правки остаются читаемыми; в таблице новые колонки пусты («—»).

## Что проверить при ревью
1. Редактор схемы — «сырой» JSON в текстовом поле (быстро, но неудобно). Нужен ли визуальный редактор полей (добавить поле кнопкой)? В хакатоне это сильно улучшило бы показ «меняем модель»; стоимость — дополнительная задача.
2. Нужен ли просмотр истории версий схем и откат.
3. Нужно ли разделение прав: админка схем только для оператора.
4. Название типов (`monitoring`) и подписи — по-русски в меню, латиницей в пути.
5. Нужна ли в списке сортировка и поиск (сейчас нет).
