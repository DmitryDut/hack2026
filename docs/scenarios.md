# Реализуемые сценарии (v2)

**Статус: черновик для ревью, вторая редакция.** Описывают, что система делает при каждом действии. Экраны — `docs/ui/`; требования — `docs/requirements.md`; тесты — `docs/SPEC.md` §12. Данные — демо-сид: партнёр `mts-link-1` (логин `mts-link-1`, пароль `demo`), услуги `svc-vcs` (Link ВКС, 4 сигнатуры, тариф Платина, 12 ч) и `svc-chat` (Link Чаты, 1 сигнатура, Золото, 24 ч), `sig-4` = `media2.mts-link.ru:5005`.
Тарифы и цены (по заданию, цена = Мбит/с × 100 ₽ × коэффициент): Бронза 10 Мбит/с ×1.0 = 1 000; Серебро 30 ×1.5 = 4 500; Золото 50 ×2.0 = 10 000; Платина 100 ×3.0 = 30 000; Бриллиант 200 ×4.0 = 80 000 ₽/мес.
Формат: актор · предусловия · шаги (действие → ответ системы) · результат · ветки · требования · автотест.

## 2. Основные сценарии

### S-01. Вход партнёра
Актор: партнёр.
1. Открывает `/login` → форма (экран 0.1); `[Подставить]` рядом с MTS Link заполняет `mts-link-1` / `demo`; `[Войти]`.
2. Система создаёт сессию (подписанный токен) → открывается `/cabinet`: шапка «Личный кабинет · MTS Link (mts-link-1)», баннер «○ Приоритет пока не включён ни для одной услуги» и список из двух услуг.
3. Альтернативный вход: из `/px-showcase` кнопка «Конфигурировать сервисы QoS» → iframe `/embed?token=…`; форма входа пропускается, кабинет открыт в режиме встраивания; `partner_id` из токена.
4. `[Выйти]` → сессия удалена, `/login`.
Ветки: N-01…N-03, N-16, N-17. Требования: EMB-1, EMB-2, NFR-4 (+ маршруты `/login`, `/cabinet` — новые, см. «Изменения в SPEC»). Тест: `test_token.py`, `test_demo_flow.py`.

### S-02. Добавление услуги и данных для настройки QoS
Актор: партнёр. Предусловия: S-01.
1. На `/cabinet` `[+ Добавить услугу]` → форма: «Link Записи», описание → `[Создать и добавить сигнатуры →]`.
2. Открывается карточка услуги, вкладка «① Данные услуги»; список сигнатур пуст.
3. `[+ Добавить сигнатуру]`: IPv4 `10.10.2.10`, URI `api.mts-link.ru`, порт `8443`, протокол `HTTPS` → строка в таблице; для второго порта добавляет ещё одну строку.
4. В услуге «Link ВКС» (из сида) видит четыре сигнатуры с IP, URI, портами и протоколами (экран 2.3).
5. Удаляет «Link Записи» → подтверждение → услуга и сигнатуры исчезают.
Результат: у услуги заполнен паспорт трафика, из которого строится настройка в сети. Ветки: N-04, N-05. Требования: DATA-4…DATA-7. Тест: `test_data_rules.py`.

### S-03. Расчёт стоимости по тарифам
Актор: партнёр. Предусловия: у «Link ВКС» есть сигнатуры.
1. Вкладка «② Тариф и стоимость»: таблица из пяти тарифов с «Скорость до», SLA, коэффициентом и **стоимостью этой услуги по каждому тарифу** (1 000 / 4 500 / 10 000 / 30 000 / 80 000 ₽/мес).
2. Выбирает «Платина» и срок «12 ч» → блок «Расчёт»: `100 Мбит/с × 100 ₽ × 3.0 = 30 000 ₽/мес`; подпись, что срок на стоимость не влияет (по формуле конфигурации).
3. Меняет выбор на «Серебро» → расчёт сразу `30 × 100 × 1.5 = 4 500 ₽/мес`; возвращает «Платина».
4. `[Подтвердить цену]` → цена услуги подтверждена, вкладка «③ Тестирование» открыта.
5. На главной в строке «Link ВКС» стоимость «30 000 ₽/мес»; внизу «в черновиках 40 000 ₽/мес» (с Link Чаты Золото 10 000).
Ветки: N-13, N-15. Требования: DATA-2, DATA-3, PROC-2, PROC-3, PROC-5. Тест: `test_pricing.py`.

### S-04. Предложение и отправка JSON в PX
Актор: партнёр. Предусловия: цены подтверждены у обеих услуг.
1. Меню «Стоимость и предложение» → таблица услуг с тарифами, стоимостью и итогом `40 000 ₽/мес`.
2. Создаёт вариант «Экономный» (ВКС на Серебре, 4 500 ₽/мес), `[Сравнить]` → таблица «услуга × вариант», итоги; выбирает «Базовый».
3. `▸ JSON для PX` → предпросмотр по формату `px-json-proposal.md` (только услуги с подтверждённой ценой).
4. `[Отправить в витрину PX]` → витрина получает `postMessage(qod:export)` и показывает карточку «Партнёр подключён» (экран 1.2) с услугами, SLA, ценами и итогом.
Результат: PX получил конфигурацию; цены совпадают с формулой. Ветки: N-15. Требования: EXP-1…EXP-4, PROC-4, MOCK-3, EMB-3. Тест: `test_export.py`, `test_pricing.py`.

### S-05. Тестирование (песочница): провал, правка, успех
Актор: партнёр. Предусловия: S-03 (цена подтверждена).
1. Карточка «Link ВКС» → вкладка «③ Тестирование» → `[Начать тест]` → «◐ Тест идёт», 4 строки `… ожидает`.
2. `[Проверить]` строк 1–3 → `✓ успех`; ставит галки подтверждения.
3. `[Проверить]` строки 4 (`media2…:5005`) → `✗ ошибка`: «BEARER_TIMEOUT: RTP-поток не отвечает: таймаут установки dedicated bearer для media2.mts-link.ru:5005» → «✗ Тест не пройден».
4. `[Вернуться к настройке]` → «○ Черновик»; на вкладке ① меняет порт `sig-4` на 5006.
5. Возвращается к тестированию, `[Начать тест]` → все 4 ✓ и подтверждены → «✓ Тест пройден».
Журнал (по `expected_event_log.json`): `run_started` → 3×(`step_checked`, `step_confirmed`) → `step_checked(error)` → `run_failed` → `run_reset` → `signature_updated` → новый `run_started` → … → `run_passed`. Требования: SBX-1…SBX-5, SBX-8, SBX-10. Тест: `test_sandbox.py`.

### S-06. Включение приоритета и признак «трафик приоритизирован»
Актор: партнёр. Предусловия: S-05.
1. Вкладка «④ Запуск и абоненты» → `▸ Показать запрос (JSON)` (блоки `camara` и `pfd`) → `[Включить приоритет]`.
2. Система вызывает мок `POST /mock-gsma/qod/sessions` → `session_id = qod-session-…`, статус `applied`.
3. **Признак приоритета появляется сразу в нескольких местах:**
   - заголовок карточки услуги: «⚡ Приоритет активен»;
   - панель «⚡ Трафик приоритизирован»: тариф Платина (до 100 Мбит/с), SLA 99.95 %, «действует с 12:07:01 до 00:07:01 (осталось 11 ч 52 мин)», список 4 сигнатур под приоритетом, `session_id`, число абонентов;
   - главная `/cabinet`: баннер «⚡ Трафик приоритизирован: 1 из 2 услуг», строка «Link ВКС» — «⚡ Приоритет активен до 00:07»;
   - витрина PX: карточка «⚡ Приоритет включён: 1 из 2 услуг» (после повторной отправки или обновления);
   - оператор: «Платина · 12 ч … ⚡ Приоритет активен».
4. Правка сигнатур теперь запрещена (N-08).
Результат: пользователь видит, что приоритет включён и до какого времени. Оговорка на экране: статус отражает включение по данным APIgw (мок), фактический трафик не измеряется. Требования: SBX-7, STD-2, STD-3, NFR-3. Тест: `test_sandbox.py`, `test_mocks.py`.

### S-07. Подключение услуги абоненту
Актор: партнёр. Предусловия: S-06.
1. Вкладка ④ → номер `+7 916 123 00 01` → `[Подключить]`.
2. Система вызывает `POST /mock-gsma/qos-assignments` (`REQUESTED`), затем `GET …` (`AVAILABLE`); в таблице абонентов строка «+7 916 123 00 01 · AVAILABLE · ⚡ Трафик приоритизирован».
3. `[Открыть карточку абонента]` → `/subscribers/+79161230001`: плашка «⚡ Трафик приоритизирован: Link ВКС · Платина», таблица услуг, таймлайн из двух событий.
Ветки: N-09, N-10, N-18. Требования: SUB-1…SUB-3. Тест: `test_demo_flow.py`.

### S-08. Наблюдение: журналы и трассировка
Актор: партнёр (свои данные), оператор (все).
1. Партнёр: меню «Журнал» — события и внешние вызовы своих услуг.
2. Оператор: `/operator` → MTS Link → «Link ВКС — ⚡ Приоритет активен, qod-session-…» → «Журнал событий» по возрастанию времени; «Внешние вызовы» — `gsma_validate` (в том числе `result: error`), `gsma_session`, `qos_assignment_create` с запросом и ответом.
3. Витрина: «Трассировка» — 17 из 17 после S-09.
Требования: SBX-8, TRC-1, TRC-2, NFR-3. Тест: `test_trace.py`, `test_sandbox.py`.

### S-09. Флоу диаграммы задания
Актор: новый партнёр.
1. `/qos_platform/landing` → форма (экран 6.1): компания, контакт, трафик → `[Отправить]`.
2. Получает `partners-1` и список тарифов из каталога; выбирает «Золото» → `[Подключить]`.
3. Карточка «Партнёр подключён: partners-1, Золото, SLA 99.9 %, 10 000 ₽/мес»; «Трассировка: 17 из 17 ✓».
4. `[Перейти в личный кабинет]` → `/cabinet` без услуг.
Требования: MOCK-1, MOCK-2, MOCK-3, TRC-1. Тест: `test_trace.py`, `test_mocks.py`.

Цель: показать, что типовые правки делаются без изменения кода и без рестарта (кроме перечитывания YAML). Целевое время — до 2 минут на правку (цель, пока не измерена).
