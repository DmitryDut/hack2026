# Реализуемые сценарии

**Статус: черновик для ревью.** Описывают, что система делает при каждом действии. Экраны — `docs/ui/`; требования — `docs/requirements.md`; тесты — `docs/SPEC.md` §12. Данные — демо-сид (`SPEC.md` §11): партнёр `mts-link-1`, сервисы `svc-vcs` (Link ВКС, 4 сигнатуры, Platinum/12 ч) и `svc-chat` (Link Чаты, Gold/24 ч), `sig-4` = `media2.mts-link.ru:5005`.
Формат: актор · предусловия · шаги (действие → ответ системы) · результат · ветки · требования · автотест.

## 1. Основные сценарии

### S-01. Вход партнёра из витрины
Актор: партнёр. Предусловия: сид загружен.
1. Открывает `/px-showcase` → видит страницу партнёра MTS Link (экран 1.1).
2. `[Конфигурировать сервисы QoS]` → открывается iframe `/embed?token=…`; в шапке «Партнёр: MTS Link (mts-link-1) — из токена»; ручного ввода `partner_id` нет.
Результат: конфигуратор открыт на шаге ① со списком сервисов партнёра. Ветки: N-01…N-03. Требования: EMB-1, EMB-2, NFR-4. Тест: `test_token.py`, часть `test_demo_flow.py`.

### S-02. Сервисы и сигнатуры
Актор: партнёр. Предусловия: S-01.
1. На шаге ① видит «Link ВКС» (4 сигнатуры) и «Link Чаты» (1).
2. `[+ Добавить сервис]` → «Link Записи» → появляется в списке со статусом «черновик».
3. В «Link ВКС» `[+ Добавить сигнатуру]`: `10.10.2.10 / api.mts-link.ru / 8443 / HTTPS` → сохранена, у сервиса 5 сигнатур.
4. Удаляет «Link Записи» → подтверждение → сервис и его сигнатуры исчезают.
Ветки: N-04, N-05. Требования: DATA-4…DATA-7. Тест: `test_data_rules.py`.

### S-03. Профиль, срок и цена
Актор: партнёр.
1. Шаг ②: для «Link ВКС» выбирает карточку Platinum и срок 12 ч → «Цена: 100 × 100 ₽ × 3.0 = 30 000 ₽/мес».
2. Для «Link Чаты» — Gold и 24 ч → 10 000 ₽/мес.
3. Шаг ③: вариант «Базовый» (оба сервиса) → итог 40 000 ₽/мес; создаёт ещё вариант «Экономный» (Silver, 4 500 ₽/мес за ВКС), `[Сравнить варианты]` → таблица.
4. Выбирает «Базовый».
Ветки: N-13, N-15. Требования: DATA-2, DATA-3, PROC-2, PROC-4, PROC-5. Тест: `test_pricing.py`.

### S-04. Подтверждение цены и отправка JSON в PX
Актор: партнёр. Предусловия: S-03.
1. Шаг ③: `▸ JSON для PX` — предпросмотр (формат `px-json-proposal.md`; сервисы с подтверждённым назначением).
2. `[Подтвердить цену]` → вариант «Базовый» = подтверждён; сервисы получают `assignment_status=confirmed`; шаг ④ становится доступным.
3. `[Отправить в витрину]` → витрина получает `postMessage(qod:export)`, показывает карточку «Партнёр подключён» (экран 1.2): сервисы, профили, SLA, цены, итог.
Результат: PX знает конфигурацию; цены совпадают с формулой. Ветки: N-15, ответ на `postMessage` чужого origin игнорируется. Требования: EXP-1…EXP-4, PROC-3, MOCK-3, EMB-3. Тест: `test_export.py`, `test_pricing.py`.

### S-05. Песочница: провал, правка, успех
Актор: партнёр. Предусловия: S-04, сервис «Link ВКС».
1. Шаг ④ `[Начать тест]` → статус «Тестируется», 4 строки `… ожидает`.
2. `[Проверить]` строк 1–3 → `✓ успех`; ставит галки подтверждения.
3. `[Проверить]` строки 4 (`media2…:5005`) → `✗ ошибка`: «RTP-поток не отвечает: таймаут установки dedicated bearer для media2.mts-link.ru:5005» → статус «Ошибка теста».
4. Возвращается: `[Вернуться к конфигурированию]` → «Черновик»; на шаге ① меняет порт `sig-4` на 5006 (если правка сделана до возврата, плашка 2.10 сообщает о сбросе).
5. `[Начать тест]` → все 4 проверены, подтверждены → «Пройден ✓».
Журнал (по `expected_event_log.json`): `run_started` → 3×(`step_checked`,`step_confirmed`) → `step_checked(error)` → `run_failed` → `run_reset` → `signature_updated` → новый `run_started` → … → `run_passed`.
Требования: SBX-1…SBX-5, SBX-8, SBX-10. Тест: `test_sandbox.py`.

### S-06. Запуск (активация)
Актор: партнёр. Предусловия: S-05 (`passed`).
1. Шаг ⑤: видит параметры запуска и `▸ Показать запрос (JSON)` (блоки `camara`, `pfd`).
2. `[Старт коммерческой эксплуатации]` → вызов `POST /mock-gsma/qod/sessions` → ответ `session_id = qod-session-…`, статус «Запущен ✓», период 12 ч.
3. В «Внешних вызовах» — запись `gsma_session` с запросом и ответом.
Результат: сервис в статусе `applied`; правка сигнатуры запрещена (N-08). Требования: SBX-7, STD-2, STD-3. Тест: `test_sandbox.py`, `test_mocks.py`.

### S-07. Подключение сервиса абоненту
Актор: партнёр. Предусловия: S-06.
1. Шаг ⑤: вводит номер `+7 916 123 00 01` → `[Подключить]`.
2. Система вызывает `POST /mock-gsma/qos-assignments` (REQUESTED), затем `GET …` (AVAILABLE).
3. Видит `✓ Подключено…`; `[Открыть карточку абонента]` → `/subscribers/+79161230001`: сервис Link ВКС, Platinum, 12 ч, таймлайн из двух событий.
Ветки: N-09, N-10. Требования: SUB-1…SUB-3. Тест: `test_demo_flow.py`.

### S-08. Наблюдение: журналы и трассировка
Актор: оператор.
1. `/operator` → партнёр MTS Link → у «Link ВКС» «Запущен», session_id.
2. «Журнал событий» — вся цепочка S-05…S-07 по времени по возрастанию.
3. «Внешние вызовы» — `gsma_validate` (в т. ч. с `result: error`), `gsma_session`, `qos_assignment_create`, запросы и ответы.
4. В витрине «Трассировка» — 17 из 17 после S-09.
Требования: SBX-8, TRC-1, TRC-2, NFR-3. Тест: `test_trace.py`, `test_sandbox.py`.

### S-09. Флоу диаграммы задания
Актор: новый партнёр. Предусловия: сид загружен.
1. `/qos_platform/landing` → форма (экран 6.1). Заполняет: компания, контакт, трафик → `[Отправить]`.
2. Получает `partners-1` и список профилей из каталога; выбирает Gold → `[Подключить]`.
3. Карточка «Партнёр подключён: partners-1, Gold, SLA 99.9 %, 10 000 ₽/мес»; `Трассировка: 17 из 17 ✓`.
4. `[Перейти в конфигуратор]` → шаг ① с пустым списком сервисов.
Требования: MOCK-1, MOCK-2, MOCK-3, TRC-1. Тест: `test_trace.py`, `test_mocks.py`.

## 3. «А теперь поменяйте вот это»
Цель: показать, что типовые правки делаются без изменения кода и без рестарта (кроме перечитывания YAML). Целевое время — **до 2 минут на правку** (цель, пока не измерена). Для каждой правки: что делаем, где, что меняется на экране, чего менять не нужно.

| ID | Просьба заказчика | Что делаем и где | Что видно | Код менять? |
|---|---|---|---|---|
| C-01 | «Добавьте уровень «Бриллиантовый+ 300 Мбит/с»» | `/entities/qos_profile` → `[+ Создать]`: код `DIAMOND_PLUS`, 300 Мбит/с, приоритет 5, множитель 5.0, SLA 99.99 | на шаге ② новая карточка; цена за 300 Мбит/с = 300 × 100 × 5.0 = 150 000 ₽/мес | нет |
| C-02 | «В сигнатуре нужен IPv6, а URI необязателен» | `/admin/schemas` → signature: добавить `ipv6` (`format: ipv6`), убрать `uri` из `required` → сохранить | в форме сигнатуры поле IPv6, URI без `*`; старые записи читаются; в таблице новая колонка | нет |
| C-03 | «Добавьте сервису SLA, % от 99 до 99.999» | `/admin/schemas` → service: `sla_percent` (min 99, max 99.999) | поле в форме сервиса; 99.5 принято, 50 → ошибка диапазона | нет |
| C-04 | «Нужна сущность «Мониторинг»» | `/admin/schemas` → `[+ Новый тип]` `monitoring` со схемой (endpoint, interval_sec ≥ 10, service_ref) | в меню раздел, CRUD работает; `interval_sec: 5` → ошибка | нет |
| C-05 | «Поменяйте расчёт цены: ставка 120 вместо 100» | `config/pricing.yaml`: `const: 100` → `120` → `[Перечитать конфиг]` | Platinum: 100 × 120 × 3.0 = 36 000 ₽/мес; пересчёт в предложениях | нет |
| C-06 | «Сначала пусть тестируют, а цену подтверждают потом» | `config/process.yaml`: поменять местами шаги ③ и ④, перенести условие (`gates`) подтверждения цены на шаг запуска → `[Перечитать конфиг]` | степпер: Сервисы → Профиль → Песочница → Предложение → Запуск; песочница доступна без подтверждённой цены; запуск — только после теста и подтверждения цены | нет* |
| C-07 | «В JSON для PX добавьте статус профиля» | `config/px_payload.yaml`: добавить `status` в `lookups.qos_profile.fields` → перечитать | в предпросмотре и в экспорте у профиля поле `status` | нет |

Как проверяем: ручной прогон на репетиции + автотест `test_change_scenarios.py` для C-01…C-05, C-07. Результат фиксируем в `docs/change-playbook.md` (задача T-011).

## Что проверить при ревью
1. **Цена и подтверждение до песочницы** (S-04, S-05): в демо-сид `svc-vcs` в `SPEC.md` §11 записан как «confirmed»; по сценарию он должен стартовать в «draft», иначе шаги ②–③ нечего показывать. Предлагаю в сиде оставить профиль выбранным, но `assignment_status = draft`; экспортный тест использует свою фикстуру (D10). Согласны?
2. **Diamond в сиде** — организаторы в задании приводят «Бриллиантовый 200 Мбит/с» как пример правки. Если оставить его в сиде, на демо придётся добавлять другой уровень (C-01 с «Бриллиантовым+»). Либо убрать Diamond из сида и добавлять его вживую.
3. **C-06** требует расширить `gates` в `SPEC.md`: `services_exist`, `profiles_set`, `offer_confirmed`, `passed`, `applied` и список условий «И».
4. Кто запускает сервис — партнёр (как в V4) или оператор; кто подтверждает результат песочницы.
5. Три «важных» допущения о тестах: ошибка в одной строке завершает прогон; сброс при правке с предупреждением; номер абонента — только из базы.
6. Нужны ли сценарии, не вошедшие сюда: отключение абонента, продление срока (extend), несколько партнёров в одной сессии демо.
