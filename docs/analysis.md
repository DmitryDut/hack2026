# Разбор задания

## 1. Суть
МТС строит QoS-платформу (QP): партнёру-сервис-провайдеру (например, MAX, «Link») оператор гарантирует качество трафика его сервисов. Практически это `QoD` (Quality on Demand) по CAMARA/GSMA Open Gateway поверх SCEF/NEF и PCRF.

В хакатоне мы делаем **фрагмент после онбординга в PX**: партнёр уже зарегистрирован, проверен, подписал контракт и получил базовый оффер. Остаётся **сконфигурировать сервисы**, пройти песочницу и включить QoS в сети. Оценивают не красоту, а **цену и скорость изменений** (NFR-2).

## 2. Процесс (шаги 3–8 UC-листа [F13])
```
 PX: регистрация (1), подключение продукта (2)   ← вне скоупа
   │  Partner_ID
   ▼
 3  Ввод сервисов и сигнатур (IPv4, URI, port, protocol)           [QoD]
 5  Справочник QoS-профилей (из NEF → QoD)                         [Resource Catalog]
 6  Назначение профилей и Duration сервисам                        [QoD]
    └─ JSON → PX → расчёт цены → партнёр подтверждает → PX подтверждает QoD
 7  Песочница: построчная проверка сигнатура×профиль×Duration      [QoD]
    ├─ успех → 8
    └─ провал → назад к 3/6
 8  Активация: вызов GSMA QoD APIgw, запись в PCEF/PCRF            [QoD → ядро]
 ──────────────────────────────────────────────
 9  CDR/EDR (вне скоупа)   10  Счёт в PX (вне скоупа)
```
В UC-листе нет шага 4; нумерация источника сохранена.

## 3. Flow-диаграмма задания (стр. 5)
Акторы: Service Provider, Partner Landing, Customer Journey (CJ), Resource Catalog (RC), Partner eXperience (PX).
- **Шаг 1 — лендинг:** `GET /qos_platform/landing` → CJ отдаёт HTML-форму (company / contact / traffic).
- **Шаг 2 — регистрация:** `POST /qos_platform/reg` → CJ → `POST /px/reg` → `{"id":"partners-1"}` (client_id). CJ запрашивает `GET /rc/qos_catalog` → `[{Gold, 50 Mbit/s}, {Silver, 30 Mbit/s}, …]` и показывает «Выбор QoS-профиля».
- **Шаг 3 — выбор профиля:** `POST /qos_platform` `{client_id, profile=Gold}` → `POST /px/save_qos` → `{"id":"qos_profiles-1"}` → «Партнёр подключён (client_id, Gold, SLA 99.9% из каталога)».

Диаграмма — упрощённая, из эпохи этапов 1–3 исходного описания. Для нашего сценария это **образец стиля интеграции**: CJ — оркестратор HTML-форм, PX и RC — внешние REST-системы. Мы реализуем их встроенными моками с теми же путями.

## 4. Что реально, а что эмулируем
| Компонент | В демо |
|---|---|
| PX (регистрация, цена, подтверждение) | встроенный мок: `Partner_ID` выдаётся им, цена — по правилу из конфига; JSON-спека — допущение до получения |
| Resource Catalog (QoS-профили) | справочник в YAML |
| QoD management (инвентори, процесс, UI) | **реализуем** |
| Песочница | реализуем (ручное подтверждение строк, как в задании) |
| GSMA QoD APIgw | мок, пишет CAMARA-подобный payload в журнал |
| SCEF/NEF/PCRF/сеть | не эмулируем (ADR 0002) |
| Абонент и подключение сервиса | запись в БД + событие + запрос в мок APIgw |

## 5. Ответ на главный критерий (гибкость, NFR-2)
Идея: **ядро — маленький универсальный движок, а всё, что меняется бизнесом, — данные**.
- Справочники (профили, протоколы, типы сервисов) — `config/*.yaml`.
- Процесс партнёра (статусы и переходы) — YAML, движок читает таблицу переходов.
- Шаблон JSON для PX — YAML-маппинг полей (спека придёт позже).
- Поля форм (например, добавить атрибут сигнатуры) — описание в YAML, UI рисуется по описанию.

Проверка: сценарий «правка после демо» (T-010) выполняется только правкой конфига и перезапуском. Решение зафиксируем в ADR 0003. Это же ответ на «стоимость поддержки»: один процесс, без Docker, без сборки.

## 6. Допущения (до получения спецификаций)
1. Профили: 5 уровней — QOS_E (экстренный), QOS_S, QOS_M, QOS_L и Gold/Silver из диаграммы. Имена и параметры (полоса, задержка, max duration, SLA) — рабочие, меняются в YAML.
2. `Duration` — целое число секунд с ограничением `max_duration` профиля.
3. Валидация сигнатур: IPv4 или URI (хотя бы одно), порт 1–65535, protocol из списка задания.
4. Цена = базовая ставка профиля × число сигнатур × коэффициент Duration; формула в YAML, чисто демонстрационная.
5. Песочница — ручное подтверждение каждой строки (как в [T 2d-i]); «неуспех» — отметка вручную.
6. Авторизация iframe — упрощена: `Partner_ID` приходит параметром, режим `?embed=1` убирает шапку.

## 7. Открытые вопросы заказчику
1. Спецификации (JSON для PX, QoS-профили, справочник сигнатур) — когда?
2. Формат и единицы Duration; поведение по окончании.
3. Правила расчёта цены и кто их задаёт.
4. Как связаны сервис партнёра и абонент: подключается ли сервис абоненту заранее («service subscription») или на каждую сессию («on-demand per session») — вопрос слайда 9 для кейса MAX [F9]. От ответа зависит наш шаг FR-13.
5. Откуда в системе берутся абоненты (MSISDN) и идентификаторы IP/IMSI (IPTOMS, [F7, F16 п.1]).
6. Как устроены security и песочница в текущем онбординге [F16 п.3].
7. Нужна ли в PoC реальная связка с PX (iframe, SSO) или достаточно макета.

## 8. Идеи на будущее (из слайдов)
Метки «LLM» в UC-листе [F13] — шаги, потенциально реализуемые LLM-driven без кода (ввод сигнатур, назначение профилей, песочница, активация). Для хакатона не берём, но конфигурируемая архитектура этому не мешает.
