# Разбор задания (v2, после получения вариантов ТЗ, 3GPP и CAMARA)

## 1. Суть
МТС продаёт партнёрам приоритет трафика (QoS). Сегодня это ручной процесс: сигнатуры, тариф, цена, тест, включение — недели. Нужен конфигуратор, где партнёр делает всё сам [S]. Сложность — не сайт, а **изменчивость правил**: уровни качества, поля анкеты, порядок шагов, расчёт цены. Организаторы после демо скажут «поменяйте вот это» и замерят время и стоимость [S, T 1c].
Партнёр уже прошёл регистрацию, проверку, контракт и получил базовый оффер в PX; наша часть — шаги 3–8 UC-листа [T 2a, F13].

## 2. Процесс
```
 (PX: регистрация, контракт, базовый оффер — вне скоупа)
 3  Ввод сервисов и сигнатур {IPv4, URI, port, protocol}
 5  Каталог QoS-профилей (справочник)
 6  Назначение профиля сервису  →  JSON в PX  →  цена  →  подтверждение
 7  Песочница: построчная проверка, ручное подтверждение; провал → назад к конфигурированию
 8  Активация: вызов GSMA QoD APIgw (мок)  →  статус Applied
 +  Подключение сервиса абоненту (MSISDN)
```
Шага 4 в источнике нет; нумерация сохранена.

## 3. Пять вариантов ТЗ и наш выбор
Варианты — готовые ТЗ на 3 часа с тестовыми данными; README советует выбрать один или комбинацию [V-README]. Решение команды: **собрать своё**, стек остаётся FastAPI + Jinja2/HTMX.

| Вариант | Что даёт | Берём? | Зачем |
|---|---|---|---|
| V2 schema-driven | модель, API, UI из JSON Schema, админка схем | **ядро** | прямой ответ на критерий «поменяйте вот это» |
| V1 CRUD-инвентори | данные, валидации, экспорт, цена | **да** | сид, эталон JSON для PX, формула цены, правила валидации реализуются поверх ядра V2 |
| V4 песочница | автомат статусов, мок APIgw, журнал | **да** | шаги 7–8 задания |
| V5 витрина + iframe | моки PX/RC, токен, postMessage, трассировка 17 реплик | **да, упрощённо** | требование встраивания и «сквозная авторизация» [T 2b-i] |
| V3 AI-агент | чат + tool calls, фолбэк | **опция** | соответствует LLM-меткам UC-листа [F13], но требует доступа к LLM-API |

Как они стыкуются: V1 — данные; V2 — как они описаны и меняются; V4 — как проходят тест и включение; V5 — как всё встроено в витрину.

## 5. Решения и допущения
1. **Стек** — оставляем FastAPI + Jinja2/HTMX [решение команды]. Формы по JSON Schema рисуем сами небольшим рендерером (вместо rjsf). Риск: рендерер надо написать (типы string/integer/number/enum/boolean, required, pattern, min/max, format); объём ограничиваем этим набором.
2. **Два приложения из V5** (витрина A и конфигуратор B) — **предложение:** держать в одном процессе как разные страницы. Токен, iframe, `postMessage` и CSP от этого не страдают, а запуск остаётся одной командой. Если организаторам важны разные origin — вынести витрину во второй процесс на другом порту (это отдельный вопрос команде).
3. **Срока приоритета нет** (решено 2026-11-03): услуга либо включена, либо выключена; Duration из задания не реализуем.
4. **QoS-профили:** 5 уровней как в [S] и V1 (Bronze…Diamond); в V5-каталоге пока 4 (без Diamond); значения SLA есть только в V5. Единый справочник собираем из V1 + SLA из V5. Тексты в CAMARA-справке (QOS_E/S/M/L) — справочный образец формата.
5. **Цена:** `Мбит/с × 100 ₽ × коэффициент тарифа` [V1, V5]; срока в формуле нет (решение 2026-11-03: коэффициент срока, добавленный ранее, отменён) — D15 в `SPEC.md`.
6. ~~**Подключение абоненту:**~~ (отменено 2026-11-03, вне скоупа) в ТЗ вариантов этого шага нет; берём из [F7] и CAMARA Provisioning [CA] (по `phoneNumber`).
7. **JSON для PX:** официальной спеки нет, формат предлагаем сами — [px-json-proposal.md](px-json-proposal.md): эталон `expected_export.json` + добавленные поля (`schema_version`, `offer`, `service_id`, `sla_percent`). Маппинг меняется конфигом.
8. **Песочница:** проверка успех/ошибка — детерминированный мок, ручное подтверждение строк по заданию [T 2d-i].

## 6. Разрывы между источниками
| Что | Источник A | Источник B | Как закрываем |
|---|---|---|---|
| Duration | часы (V1, S) | секунды (CQ `duration`) | не реализуем: срока нет |
| URI и protocol сигнатуры | есть в задании | нет в CAMARA (`applicationServer` — IP, порты) | URI/protocol идут в PFD (`urls`, `domainNames`, `flowDescriptions`) и в JSON для PX |
| Лимиты | — | ≤16 IP на сессию (CQ) | проверка при активации, предупреждение |
| Профиль на устройство | QoD-сессия на время (CQ) | Provisioning бессрочно на всё устройство (CA) | для абонента берём Provisioning; сессию — как вариант (вопрос 4) |
| Профили | 5 уровней (S, V1) | 4 в V5 каталоге | единый справочник |
| Номер шага | UC-лист [F13] | нет шага 4 | сохраняем нумерацию источника |

Что дают 3GPP-файлы: **PFD Management** (`pfds` с `flowDescriptions`, `urls`, `domainNames`, `dnProtocol`) — стандартный способ передать сети «паспорт трафика»; **AsSessionWithQoS** (`flowInfo`, `qosReference`, `qosDuration`, `events`, `notificationDestination`) — то, во что платформа превращает QoD-запрос на стороне SCEF/NEF [F3, F5]. В прототипе мы их не вызываем, а показываем соответствие в payload мока.
