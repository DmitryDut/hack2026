# Требования (ФТ / НФТ)

Метки источников — в `source/README.md`: **[T]** задание, **[F]** отзыв команды, **[M]** MVP-рекомендации и пересказ, **[S]** «простыми словами», **[V1…V5]** варианты ТЗ (F*/A* — их пункты), **[3G]** 3GPP, **[CP]/[CQ]/[CA]** CAMARA. Разбор и допущения — `analysis.md`. Статус каждого требования: **Базовое** (делаем) / **Опция** (если останется время).

## 1. Цель и критерий оценки
Прототип QoD management: партнёр сам конфигурирует сервис (сигнатуры, QoS-профиль), видит цену, тестирует в песочнице и включает приоритет без ручных заявок [S, M].
**Главный критерий:** после показа рабочей версии организаторы просят «поменяйте вот это» и меряют время и стоимость правки. Система должна переживать типовые изменения за минуты, без переписывания кода [S, T 1, T 5].
Типовые правки из задания: новый уровень качества («Бриллиантовый 200 Мбит/с»), новое поле (IPv6), другой порядок шагов, другой расчёт цены [S]; смена схемы сигнатуры, новая сущность «Мониторинг», новое поле SLA с диапазоном [V2 `demo_change.json`].

## 2. Скоуп
**Входит:** конфигурирование сервисов после онбординга → цена → песочница → активация (мок GSMA APIgw); моки PX и каталога; встраивание в витрину.
**Не входит:** подключение услуг к конечным абонентам (решено 2026-11-03: платформа работает с партнёрами); регистрация, проверка и контракт партнёра как процесс (в демо — только мок-регистрация шагов 1–2 диаграммы [V5]); CDR/EDR и счёт (шаги 9–10 UC-листа [F13]); реальные SCEF/NEF/PCRF и радиосеть; реальная авторизация (CAPIF/OAuth).
**Опция:** AI-агент как интерфейс [V3, F13 «LLM»].

### SUB — подключение к абонентам: не делаем
Решено 2026-11-03: платформа работает с партнёрами, а не с конечными абонентами — подключение услуги к абоненту не делаем. Требования SUB-1…SUB-3 сняты; CAMARA QoS Provisioning не используется.

## 5. Приёмка
Сводные критерии (наблюдаемое действие → результат) по блокам:

| Блок | Критерии | Источник |
|---|---|---|
| CORE | Нарушение схемы → 422 с полем; смена схемы видна в UI без рестарта; новая сущность «Мониторинг» целиком из админки; невалидная схема → 422, старая цела; старые записи читаются | V2 A1–A8 |
| DATA | Порт 70000 и протокол SMTP отклоняются; дубликат → 409; удаление сервиса каскадное | V1 A1–A3, A7 |
| EXP | Экспорт после демо совпадает по структуре с `expected_export.json` | V1 A5, V2 A6 |
| PROC/MOCK | Предложение показывает сервис, профиль, цену по формуле (30 000 для Платины; 10 000 для Золота) | V1 A6, V5 A5 |
| EMB | Мусорный и истёкший токен → ошибка; порт 0 или FTP не уходят в витрину; postMessage не уходит на чужой origin | V5 A1–A4, A7, A8 |
| TRC | В журнале все 17 реплик по порядку | V5 A6 |
| SBX | Тест с падающей 4-й сигнатурой → Failed; правка сбрасывает в Draft; Passed → Applied с `session_id`; в Applied правка отклонена; журнал полный; чужой партнёр не виден | V4 A1–A9 |

**«Поменяйте вот это» — обязательный набор правок** (проверяется на репетиции, см. `docs/change-playbook.md` в задаче T-011):
1. Добавить тариф «Бриллиант+ 300 Мбит/с» (или другой новый уровень).
2. Добавить в сигнатуру поле `ipv6`, сделать `uri` необязательным.
3. Добавить в сервис поле `sla_percent` с диапазоном 99–99.999.
4. Добавить сущность «Мониторинг».
5. Изменить формулу цены и/или множители.
6. Поменять порядок шагов процесса.
7. Добавить поле в JSON для PX.
