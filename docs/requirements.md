# Требования

Источники: **[T]** — `source/01-task…v5.pdf` (задание), **[F]** — `source/02-team-feedback…pdf` (слайды). Разбор — `analysis.md`.

## Цель
Прототип процесса управления сервисами партнёра в QoS-платформе (QoD management): ввод сервисов и сигнатур, назначение QoS-профилей и Duration, выдача JSON в PX, тест в песочнице, запуск в коммерческую сеть. Результат — **демо**. Цель упражнения — сравнить варианты реализации по **минимальной стоимости, скорости внесения изменений и гибкости для бизнес-заказчика** [T, вводный абзац]. Гибкость и стоимость поддержки оценят **правкой сценариев после первого демо** [T 1c].

## Скоуп
**Входит:** шаги 3–8 UC-листа PoC [F13]: описание сервисов и сигнатур → QoS-профили (справочник) → назначение профилей и Duration → JSON в PX → подтверждение цены → песочница → активация (эмуляция вызова GSMA QoD APIgw). Плюс по запросу команды: **подключение активированного сервиса конкретному абоненту (MSISDN)** (идея из HLD [F7]: «в QP провижинится доступность сервиса Y для абонента X»).

**Не входит:**
- регистрация и проверка партнёра, контракт, базовый оффер — уже пройдены в PX [T 2a];
- runtime-сессии CAMARA QoD (`/sessions`, extend, события), SCEF/NEF/PCRF, реальная радиосеть [F3, F13];
- CDR/EDR и выставление счёта, шаги 9–10 [F13];
- реальная интеграция с PX и GSMA APIgw — эмулируем (ADR 0002).

## Функциональные требования
| ID | Требование | Источник |
|---|---|---|
| FR-1 | Партнёр идентифицируется условным `Partner_ID`, переданным из PX; все данные привязаны к нему | T 2b |
| FR-2 | Партнёр создаёт сервисы (пример: «Link ВКС», «Link Чаты») | T 2a-i |
| FR-3 | Каждому сервису — набор статичных сигнатур `{IPv4, URI, port, protocol}`; транспорт: RTP/TCP/UDP, прикладной: HTTP/HTTPS/DNS/IMAP/POP3/SSH | T 2a-i |
| FR-4 | Справочник QoS-профилей (≈5 уровней; Duration) для передачи в ядро (GSMA APIgw/CAMARA) | T 2a-ii, F3 (4), F13 (5) |
| FR-5 | Партнёр назначает сервисам QoS-профили из тех, что входят в его базовый оффер, и Duration | T 2a-iii, F13 (6) |
| FR-6 | Данные регистрируются в ресурсно-сервисном инвентори, доступны методы чтения/записи хранилища | T 2b, T 4 |
| FR-7 | Формируется JSON по спецификации PX с сервисами, сигнатурами, профилями и Duration; отдаётся в PX | T 2b |
| FR-8 | Партнёр подтверждает предложенную PX цену; после этого PX подтверждает продолжение в QoD management | T 2c |
| FR-9 | Песочница: построчный проход по сигнатурам с профилем и Duration, ручное подтверждение корректности каждой строки | T 2d-i |
| FR-10 | Успешная песочница → шаг запуска; неуспешная → возврат на конфигурирование сервисов | T 2d-iii |
| FR-11 | Песочница даёт полный контроль над изменениями и ограничивает действия ресурсами партнёра | T 2d |
| FR-12 | Активация: QoD management «вызывает GSMA QoD APIgw» и передаёт данные для эксплуатации (эмуляция, payload виден в журнале) | T 2e, F13 (8) |
| FR-13 | Подключение активированного сервиса абоненту по MSISDN, карточка абонента | запрос команды, F7 |
| FR-14 | Журнал всех переходов и внешних вызовов (наблюдаемость) | T 1a |
