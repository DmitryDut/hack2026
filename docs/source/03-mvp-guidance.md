# Рекомендации по подготовке MVP

Источник: обсуждение кейса (сообщение, полученное 2026-11-03). Приводится дословно.

---

Вот как можно подготовить прототип для сценария из твоих материалов:

1. Определи ключевой процесс: после онбординга партнера — конфигурирование сервисов, выбор характеристик сервисов, назначение QoS-профилей.
2. Сделай простой web-интерфейс (по сути — форму), где заполняются: перечень сервисов, их сигнатуры, ресурсы и профили качества.
3. UI должен позволять вносить изменения в параметры сервисов, выбирать из справочников ресурсы, видеть базовые QoS-профили.
4. По итогам заполнения данных интерфейс формирует структуру JSON согласно спецификации, пример которой должен быть выдан или согласован с продуктовой командой.
5. Далее этот JSON отдаётся в демо-режиме в sandbox API (или мок-сервис), а результат отображается пользователю для быстрой проверки сценария.
6. Результат: у тебя минимальный MVP, где можно быстро создавать, редактировать, и тестировать варианты продуктового предложения для разных сервисов партнера.

Кратко: твой прототип — это упрощенная интерактивная форма с динамическим выбором ресурсов и профилей, генерацией итогового JSON-продукта и возможностью изменить настройки до коммерческого запуска. Этого достаточно для сбора обратной связи и проверки гипотезы.

## Что известно из задачи (пересказ заказчика, 2026-11-03)

Сегодня: партнёр просит «быстрый сервис видеосвязи» → сотрудники оператора вручную выясняют сигнатуры (адреса, порты, протоколы), подбирают тариф качества («серебро» — до 30 Мбит/с, «платина» — до 100 Мбит/с), согласуют цену, тестируют и включают. Каждое изменение — заявки и ручной труд.

Проект: сайт-конфигуратор, где партнёр сам заполняет данные сервиса, выбирает качество и срок в часах, система считает цену, партнёр соглашается, система проводит тест, при успехе приоритет включается автоматически.

Главная сложность — не сайт, а то, что правила меняются: новые уровни качества («Бриллиантовый: 200 Мбит/с»), новые поля (IPv6), порядок шагов, расчёт цены. Изменения должны делаться за часы, а не месяцы.

Проверка на хакатоне: сначала рабочая версия, затем организаторы говорят «а теперь поменяйте вот это» и измеряют время и стоимость изменения.
