# ТЗ. Вариант 5 — Витрина PX + iframe-интеграция (сквозной scenario-flow)

**Хакатон по вайбкодингу, 3 часа. Самодостаточный документ: можно копировать целиком в ИИ-ассистент.**

---

## 1. Что строим

Два приложения, взаимодействующие по sequence-диаграмме из кейса (17 сообщений): **витрина PX** (мок партнёрской витрины МТС) и **QoD management** (конфигуратор сервисов/сигнатур/профилей). QoD-интерфейс встраивается в витрину через **iframe со сквозной передачей Partner_ID** (подписанный HMAC-токен), по завершении возвращает в витрину JSON, витрина рассчитывает продуктовое предложение. Каждая реплика диаграммы логируется с номером — трассировка доказывает соответствие спецификации.

Требование кейса: «предполагается встраивание Iframe в витрину PX или другие варианты, которые будут обеспечивать сквозную авторизацию и необходимый уровень безопасности».

## 2. Контекст кейса (для ИИ-ассистента)

Участники флоу (из диаграммы): Service Provider (партнёр, браузер) → Partner Landing (web-фасад QoD) → Customer Journey (оркестратор) → Resource Catalog (справочник QoS-профилей) и Partner eXperience (PX, хранилище партнёров). Партнёр регистрируется, выбирает QoS-профиль из каталога (Gold 50 Мбит/с, Silver 30 Мбит/с, …), получает подтверждение «Партнёр подключён» с SLA 99.9%. Встраивание QoD-конфигуратора — iframe в витрину PX, авторизация сквозная (токен с partner_id).

## 3. Стек (фиксированный)

- **Приложение A «Витрина PX»:** React 18 + Vite, порт 5173
- **Приложение B «QoD management»:** FastAPI + SQLite (`px.db`), порт 8000, отдаёт и свой мини-UI (embed-страницу)
- **Связь:** iframe (A встраивает страницу B) + `postMessage` для возврата JSON; HMAC-SHA256 токен (секрет в env `PX_SECRET`)
- Оба приложения — в одном репозитории, запуск двумя командами

## 4. Sequence-flow (реализовать точно; номера = трассировка)

```
Шаг 1 — landing
 1. GET  /qos_platform/landing            Service Provider → Partner Landing
 2. GET  /cj/qos_platform (empty)         Partner Landing → Customer Journey
 3. ←     content: HTML landing (form company/contact/traffic)
 4. ←     200 text/html

Шаг 2 — регистрация партнёра
 5. POST /qos_platform/reg (form)         Service Provider → Partner Landing
 6. POST /cj/qos_platform (user=«отправил форму»)   Partner Landing → Customer Journey
 7. POST /px/reg (partners, {company, contact, traffic})   Customer Journey → PX
 8. ←     200 {"id": "partners-1"}  — client_id партнёра
 9. GET  /rc/qos_catalog                  Customer Journey → Resource Catalog
10. ←     [{Gold, 50 Mbit/s}, {Silver, 30 Mbit/s}, …]
11. ←     content: HTML «выбор QoS-профиля»
12. ←     200 text/html

Шаг 3 — выбор профиля
13. POST /qos_platform (form: client_id=partners-1, profile=Gold)   Service Provider → Partner Landing
14. POST /cj/qos_platform (user=«отправил форму»)   Partner Landing → Customer Journey
15. POST /px/save_qos (qos_profiles, {client_id, profile})   Customer Journey → PX
16. ←     {"id": "qos_profiles-1"}
17. ←     content: HTML «Партнёр подключён» (client_id, Gold, SLA 99.9% из каталога)
```

Роли в прототипе (упрощение, честно проговорить на демо): браузер партнёра = Service Provider; Partner Landing = приложение A (витрина); Customer Journey = оркестрационный слой приложения A (bff-роуты); Resource Catalog и PX = приложение B (QoD management: справочник + хранилище). Флоу сообщений 1–17 сохраняется дословно, включая промежуточные роуты.

## 5. Функциональные требования

| # | Требование |
|---|---|
| F1 | Витрина A: страница партнёра «Конфигурировать сервисы QoS» — открывает iframe с embed-страницей B |
| F2 | Embed-URL: `/embed?token=<HMAC(partner_id, PX_SECRET)>&expires=<ts>`; B проверяет подпись и срок, достаёт partner_id — **ручного ввода partner_id нет** |
| F3 | Истёкший/кривой токен: страница ошибки «токен недействителен», без загрузки конфигуратора |
| F4 | В iframe (приложение B): форма — сервисы, сигнатуры {ipv4, uri, port, protocol}, выбор QoS-профиля из каталога, Duration; валидация значений |
| F5 | Каталог: `GET /rc/qos_catalog` возвращает профили из `test_data/qos_catalog.json` (Gold 50 Мбит/с SLA 99.9%, Silver 30 Мбит/с SLA 99.5%, …) |
| F6 | По завершении B отправляет наружу `postMessage({type: 'qod:export', payload: <export JSON>}, targetOrigin)`; витрина слушает и принимает только свой origin |
| F7 | Витрина рассчитывает предложение: `цена = bitrate_mbps × 100 ₽/мес × price_multiplier` и показывает карточку «Партнёр подключён»: client_id, профиль, SLA из каталога (сообщение 17) |
| F8 | **Трассировка:** каждый переход флоу (реплики 1–17) логируется в общий журнал (панель в витрине) с номером, методом, путём, timestamp; покрываются все 17 |
| F9 | Заголовки безопасности iframe на B: `X-Frame-Options: ALLOW-FROM` не используется; `Content-Security-Policy: frame-ancestors 'self' http://localhost:5173`; CORS для POST-роутов — только origin витрины |
| F10 | Фолбэк: кнопка «Открыть в новой вкладке» — тот же token-URL (если iframe заблокирован окружением) |

## 6. Сценарий демо (6 минут)

1. Открыть витрину A → страница партнёра → «Конфигурировать сервисы QoS».
2. Показать: внутри витрины iframe с формой B; partner_id виден в шапке (из токена, руками не вводился).
3. Заполнить: сервис «Link ВКС», 2 сигнатуры, профиль Gold, Duration 12H → «Отправить в витрину».
4. Витрина получила postMessage → карточка «Партнёр подключён: partners-1, Gold, SLA 99.9%, цена 50×100×2.0 = 10 000 ₽/мес».
5. Открыть панель «Трассировка сообщений»: цепочка 1–17 с методами и путями.
6. Испортить токен (вручную в URL подставить мусор) → страница ошибки (F3).
7. (Опционально) фолбэк в новой вкладке (F10).

## 7. Критерии приёмки — как мы поймём, что результат достигнут

> Проверка = действия в браузере + наблюдение журнала трассировки. Ключ: флоу соответствует диаграмме, авторизация сквозная, JSON доезжает до витрины.

| # | Как проверяем | Успех = |
|---|---|---|
| A1 | Открыть витрину → «Конфигурировать сервисы» | iframe загружен; в шапке partner_id из токена; ручного ввода partner_id нигде нет |
| A2 | Подменить токен в embed-URL на `garbage` | Страница ошибки, конфигуратор не загрузился, в БД обращений с валидным partner_id не появилось |
| A3 | Подменить expires на прошедшее время | Токен отклонён (истёк), сообщение об ошибке |
| A4 | Отправить в форме сигнатуру с портом 0 или протоколом FTP | Отклонено валидацией внутри iframe, в витрину ничего не уходит |
| A5 | Заполнить и отправить корректную конфигурацию | Витрина показала карточку «Партнёр подключён» с client_id, профилем, SLA 99.9% и ценой по формуле F7 |
| A6 | Открыть журнал трассировки | Присутствуют все реплики 1–17 с методами/путями; порядок соответствует диаграмме |
| A7 | Инспектировать Network | Каталог получен из `/rc/qos_catalog` (профили как в `qos_catalog.json`); postMessage не ушёл на чужой origin |
| A8 | Кнопка «Открыть в новой вкладке» | Открывается standalone с тем же токеном; отправка JSON работает и из вкладки (callback-режим) |
| A9 | Перезапустить демо с чистой БД (скрипт пересева) | Весь сценарий A1–A8 проходит заново без правки кода |

**Демо считается успешным**, если A1–A9 выполнены в одном браузере без ручной настройки окружения.

## 8. Тестовые данные (`test_data/`)

- `qos_catalog.json` — каталог профилей Resource Catalog (со SLA и множителями).
- `token_test_vectors.json` — токены для A2–A3: валидный, мусорный, истёкший (с expectation).
- `flow_trace_template.json` — эталон трассировки: 17 реплик с методами/путями/направлениями.
- `expected_px_offer.json` — эталон карточки «Партнёр подключён» после демо-конфигурации.
