# ТЗ. Вариант 3 — AI-агент конфигурирования «сырой текст → инвентори»

**Хакатон по вайбкодингу, 3 часа. Самодостаточный документ: можно копировать целиком в ИИ-ассистент.**

---

## 1. Что строим

QoD management с ИИ-агентом в качестве основного интерфейса. Партнёр и оператор общаются с инвентори через чат: агент создаёт/изменяет сервисы, сигнатуры, QoS-профили через tool calls, показывает результат и просит подтверждение перед записью. Агент принимает ввод в свободной форме и «сырые» спецификации (markdown/plain text) — реализация подхода «контента достаточно, чтобы скормить агенту в сыром виде» и LLM-меток на UC-диаграмме кейса (шаги 3–8).

Обычный CRUD (форма/таблица) сохраняется как **фолбэк-режим** — страховка на случай недоступности LLM на площадке.

## 2. Контекст кейса (для ИИ-ассистента)

МТС строит QoS-платформу: партнёры (MTS Link) описывают сервисы («Link ВКС», «Link Чаты») сигнатурами `{IPv4, URI, port, protocol}` и назначают QoS-профили (5 уровней) и Duration. Спецификации справочников предоставляются в сыром виде (текстом), без формальных схем. Ввод выполняет ИИ-агент, разбирающий свободный текст и вызывающий инструменты инвентори; записи валидируются и требуют подтверждения.

## 3. Стек (фиксированный)

- **LLM:** OpenAI API (gpt-4o / gpt-4o-mini) или Anthropic Claude API — через официальный SDK, режим **function/tool calling**
- **Backend:** Python 3.11+, FastAPI, SQLite (`qod.db`) — та же модель данных, что в варианте 1
- **Frontend:** React 18 + Vite: слева чат, справа live-таблица инвентори (обновляется после каждого tool call)
- Ключ API — из переменной окружения `LLM_API_KEY`

## 4. Инструменты агента (tool calls — контракт фиксированный)

| Инструмент | Параметры | Действие |
|---|---|---|
| `list_catalogs` | — | Возвращает справочники: протоколы, QoS-профили, Duration |
| `create_service` | partner_id, name, description | Создаёт сервис; возвращает id |
| `add_signature` | service_id, ipv4, uri, port, protocol | Добавляет сигнатуру; валидация значений |
| `assign_qos` | service_id, qos_profile_code, duration_code | Назначает профиль и длительность |
| `list_services` | partner_id | Список сервисов партнёра со сигнатурами и назначениями |
| `delete_signature` | signature_id | Удаляет сигнатуру |

**Правила агента (в системный промпт):**
1. Запись только через инструменты; свободный SQL/text-response не меняет данные.
2. Перед вызовом create/add/assign с новыми данными — показать пользователю карточку «собираюсь записать: …» и получить подтверждение (кнопка в чате).
3. Невалидные значения (порт вне 1–65535 и т.п.) не пробрасывать в инструмент повторно — объяснить ошибку пользователю.
4. Если пользователь просит то, чего нет в справочнике (профиль, протокол) — сообщить список допустимых значений.
5. Сырая спецификация: сначала извлечь записи, показать таблицей, потом создавать по подтверждению.

## 5. Функциональные требования

### 5.1 Инвентори (обязательно)
| # | Требование |
|---|---|
| F1 | CRUD API как в варианте 1: Partner, Service, Signature, QoSProfile, Duration + assignment (см. `../variant_1_crud_inventory/ТЗ.md` разделы 4–5; модель идентична) |
| F2 | Валидация на бэкенде: ipv4, port 1–65535, protocol из справочника, дубликат → 409 |

### 5.2 Агент (обязательно)
| # | Требование |
|---|---|
| F3 | Чат-UI: сообщения пользователя/агента, карточки подтверждения (да/нет), журналы tool calls |
| F4 | Запрос из `test_data/chat_scenarios.json` сценарий C1: создаёт сервис+сигнатуры+профиль из свободного текста за ≤4 tool calls |
| F5 | Загрузка сырой спецификации (`test_data/raw_specification.md`): агент извлекает справочники, показывает таблицей, создаёт по подтверждению |
| F6 | Ошибки валидации от инструмента агент превращает в объяснение пользователю и предложение исправить (сценарий C3) |
| F7 | Журнал действий: каждый tool call с параметрами, timestamp, результат; панель «Что сделал агент» |
| F8 | Экспорт JSON для PX: `GET /api/v1/partners/{partner_id}/export` — как в варианте 1 |

### 5.3 Фолбэк (обязательно)
| # | Требование |
|---|---|
| F9 | При недоступности LLM (таймаут/ошибка) чат показывает баннер «LLM недоступен, включён ручной режим», а CRUD-формы (упрощённые) продолжают работать |
| F10 | Переключатель «Режим: агент / ручной» в шапке |

## 6. Сценарий демо (6 минут)

1. **(1.5 мин) Сырая спецификация:** вставить в чат текст из `raw_specification.md` → агент показывает извлечённые справочники таблицей → подтверждение → справочники загружены.
2. **(1.5 мин) Свободный текст:** сценарий C1: «Заведи сервис Link ВКС…» → карточка подтверждения → сервис+2 сигнатуры+Platinum созданы; правая панель обновилась.
3. **(1 мин) Ошибка:** сценарий C3: порт 99999 → агент объясняет и предлагает 443 → принято.
4. **(1 мин) Отчёт:** «Покажи все сервисы mts-link-1 с Platinum» → структурированный ответ (list_services).
5. **(1 мин) Экспорт:** `GET /api/v1/partners/mts-link-1/export` → JSON; (опционально) переключить в ручной режим — работает без LLM.

## 7. Критерии приёмки — как мы поймём, что результат достигнут

> Проверка = прогнать сценарии из `test_data/chat_scenarios.json` и наблюдать поведение. Агент работает только через инструменты; вся запись валидируется и подтверждается.

| # | Как проверяем | Успех = |
|---|---|---|
| A1 | Сценарий C1 (создание сервиса из свободного текста) | Сервис, 2 сигнатуры, назначение Platinum/12H появились в инвентори; в журнале видно ≤4 tool calls; перед записью было подтверждение |
| A2 | Сценарий C2 (загрузка сырой спецификации) | Все 9 протоколов и 5 профилей из `raw_specification.md` созданы; показаны таблицей до создания |
| A3 | Сценарий C3 (невалидный порт 99999) | Агент НЕ вызвал `add_signature` с 99999 повторно (или вызов отклонён валидацией); пользователю объяснена ошибка; после исправления на 443 сигнатура создана |
| A4 | Сценарий C4 (несуществующий профиль `SUPER`) | Агент сообщил список допустимых кодов профилей; запись не создана |
| A5 | Журнал действий | Каждый tool call виден с параметрами и результатом; количество записей в журнале = числу фактических вызовов |
| A6 | Отключить `LLM_API_KEY` (или заблокировать сеть) и отправить сообщение | Баннер «ручной режим»; CRUD-формы работают; экспорт работает |
| A7 | `GET /api/v1/partners/mts-link-1/export` после C1 | JSON по структуре `test_data/expected_export.json` |
| A8 | Устойчивость: подряд выполнить C1 → C3 → C4 → C1' (повторное создание) | Второй C1 не ломает состояние; дубликаты сигнатур отклоняются (409 показан в чате как объяснение) |

**Демо считается успешным**, если A1–A8 выполнены, при этом ни одно изменение данных не произошло без tool call + подтверждения (кроме загрузки справочников после явного «да»).

## 8. Тестовые данные (`test_data/`)

- `raw_specification.md` — «сырая» спецификация (как из письма/Confluence): протоколы, профили, длительности текстом.
- `chat_scenarios.json` — сценарии C1–C4 с текстами сообщений, ожидаемыми tool calls и результатами.
- `seed.json` — сид инвентори (партнёр mts-link-1, справочники пусты — их загрузит агент из C2, либо предзаполнить при нехватке времени).
- `expected_export.json` — эталон экспорта после C1 (совпадает с вариантом 1).
