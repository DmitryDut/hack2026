# ТЗ. Вариант 1 — CRUD-инвентори «QoD management»

**Хакатон по вайбкодингу, 3 часа. Самодостаточный документ: можно копировать целиком в ИИ-ассистент.**

---

## 1. Что строим

Веб-приложение «ресурсно-сервисный инвентори» для QoS-платформы (QoD management). Оператор и партнёр ведут справочники: партнёры → сервисы → сигнатуры трафика → QoS-профили. Результат работы — JSON-выгрузка для партнёрской витрины (PX), по которой витрина рассчитывает продуктовое предложение.

**Границы (out of scope):** онбординг партнёра, контракты, авторизация (Partner_ID приходит из мока), реальное ядро сети. Всё это — заглушки.

## 2. Контекст кейса (1 абзац, для ИИ-ассистента)

МТС строит QoS-платформу: партнёры (например, MTS Link) описывают свои сервисы («Link ВКС», «Link Чаты») наборами статичных сигнатур `{IPv4, URI, port, protocol}` и назначают им QoS-профили и Duration. Эта конфигурация регистрируется в инвентори (QoD management), привязанном к Partner_ID, и выгружается в PX в виде JSON для расчёта продуктового предложения. Этапы 3–8 общего процесса; данный вариант покрывает этап конфигурирования и выгрузки.

## 3. Стек (фиксированный, для скорости)

- **Backend:** Python 3.11+, FastAPI, SQLAlchemy, SQLite (файл `qod.db`)
- **Frontend:** React 18 + Vite, таблицы и формы (можно Ant Design или plain CSS)
- **Запуск:** `uvicorn app.main:app --reload` и `npm run dev` (или отдать статику FastAPI-ом — на выбор)
- Валидация — Pydantic-схемы.

## 4. Модель данных

```
Partner:    id (uuid), partner_id (строка, напр. "mts-link-1"), name, status enum(active, draft)
Service:    id, partner_id FK, name, description
Signature:  id, service_id FK, ipv4, uri, port (1..65535), protocol enum
QoSProfile: id, code (BRONZE..PLATINUM), name, bitrate_mbps, priority_level
Duration:   id, code, hours (int)
Assignment: id, service_id FK, qos_profile_id FK, duration_id FK, status enum(draft, confirmed)
```

Справочники `Protocol`, `QoSProfile`, `Duration` — предзаполнить сид-данными из `test_data/seed.json` (см. раздел 8).

**Справочник Protocol (enum, 10 значений):** транспорт — `RTP, TCP, UDP`; прикладной — `HTTP, HTTPS, DNS, IMAP, POP3, SSH`.

## 5. Функциональные требования

### 5.1 CRUD (обязательно)
| # | Требование |
|---|---|
| F1 | Создание/просмотр/редактирование/удаление партнёров, сервисов, сигнатур, назначений (assignment) |
| F2 | Связь Service↔Signature один-ко-многим: у сервиса 1..N сигнатур |
| F3 | Валидация на бэкенде: ipv4 — 4 октета 0–255; port — целое 1–65535; protocol — только из справочника; uri — непустая строка |
| F4 | При удалении сервиса каскадно удаляются его сигнатуры и assignment |
| F5 | Дубликаты сигнатур (ipv4+uri+port+protocol в рамках одного сервиса) отклоняются с HTTP 409 |

### 5.2 Экспорт JSON для PX (обязательно)
| # | Требование |
|---|---|
| F6 | `GET /api/v1/partners/{partner_id}/export` возвращает JSON по схеме из `test_data/expected_export.json` |
| F7 | В выгрузку попадают только сервисы с назначенным профилем и статусом `confirmed` |
| F8 | Пустой партнёр (нет сервисов) → 200 с `"services": []` |

### 5.3 Мок витрины PX (минимум)
| # | Требование |
|---|---|
| F9 | Страница `/mock-px?partner_id=mts-link-1`: читает export-JSON и рендерит продуктовое предложение: список сервисов, профиль, duration, цена = `bitrate_mbps × 100 ₽/мес × multiplier(qos)` (Bronze=1, Silver=1.5, Gold=2, Platinum=3) |

## 6. Сценарий демо (5 минут, репетируется заранее)

1. Открыть список партнёров → партнёр «MTS Link» уже создан (сид).
2. Создать сервис «Link ВКС» → добавить сигнатуры из сценария (см. `test_data/demo_script.md`).
3. Назначить профиль Platinum, Duration 12h → подтвердить.
4. Попытаться сохранить порт 99999 → система отклоняет, показывает ошибку.
5. Открыть `/mock-px?partner_id=mts-link-1` → продуктовое предложение с ценой.

## 7. Критерии приёмки — как мы поймём, что результат достигнут

> Проверка пунктов = запустить приложение и выполнить действия. Каждый пункт формулируется как наблюдаемый результат, а не как «сделать X».

| # | Как проверяем | Успех = |
|---|---|---|
| A1 | Создать сигнатуру с портом `70000` через форму и через API (`POST /api/v1/signatures`) | Оба запроса отклонены (422/400), в БД записи нет, сообщение об ошибке видно в UI |
| A2 | Создать сигнатуру с protocol `SMTP` (нет в справочнике) | Отклонено, сообщение «недопустимый протокол» |
| A3 | Создать дубликат сигнатуры (те же ipv4+uri+port+protocol, тот же сервис) | HTTP 409, в списке сигнатур сервиса остаётся одна запись |
| A4 | Выполнить шаги 1–4 из `test_data/demo_script.md` | Все шаги проходят без ошибок, без правок кода |
| A5 | `GET /api/v1/partners/mts-link-1/export` после демо-сценария | Структура JSON идентична `test_data/expected_export.json` (те же ключи, UUID-ы и timestamp могут отличаться) |
| A6 | Открыть `/mock-px?partner_id=mts-link-1` | Видны сервис, профиль, длительность и цена, рассчитанная по формуле F9 |
| A7 | Удалить сервис «Link Чаты» (создан сидом) | Сервис, его сигнатуры и assignment исчезают из БД и UI |

**Демо считается успешным**, если A1–A7 выполнены подряд за ≤5 минут без перезапуска и правок кода.

## 8. Тестовые данные

Каталог `test_data/` рядом с этим ТЗ:
- `seed.json` — сид-данные для инициализации БД (справочники + партнёр + 1 сервис с сигнатурами + assignment).
- `expected_export.json` — эталон выгрузки для партнёра `mts-link-1` после выполнения демо-сценария.
- `demo_script.md` — пошаговый сценарий демо с конкретными значениями.
- `invalid_signatures.json` — набор невалидных сигнатур для проверки A1–A3 (каждая с ожидаемой ошибкой).
