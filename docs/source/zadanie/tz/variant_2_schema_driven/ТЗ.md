# ТЗ. Вариант 2 — Schema-driven платформа «конфигурируй без кода»

**Хакатон по вайбкодингу, 3 часа. Самодостаточный документ: можно копировать целиком в ИИ-ассистент.**

---

## 1. Что строим

Платформу QoD management, в которой **модель данных, API и UI описываются конфигурацией (JSON Schema), а не кодом**. Сущности кейса (партнёры, сервисы, сигнатуры, QoS-профили) — стартовый набор, заданный схемами в БД. Админка схем позволяет менять модель на лету: добавлять поля, сущности, обязательность — UI и API подхватывают изменения без деплоя и правки кода.

Это прямой ответ на ключевое требование кейса: «процесс, модель данных, API и UI могут конфигурироваться динамически и меняться без полного цикла разработки» — и на сценарий оценки: «после первого демо закажут корректировку сценариев».

## 2. Контекст кейса (для ИИ-ассистента)

МТС строит QoS-платформу (QoD management): партнёры описывают сервисы, сигнатуры трафика `{IPv4, URI, port, protocol}` и QoS-профили. Требование гибкости — модели и интерфейсы должны меняться конфигурацией, потому что требования будут корректировать после каждого демо. Классический CRUD писать кодом — слишком дорого в сопровождении.

## 3. Стек (фиксированный)

- **Backend:** Python 3.11+, FastAPI, SQLite (`qod.db`), хранение сущностей — JSON-колонки
- **Frontend:** React 18 + Vite + [`react-jsonschema-form`](https://github.com/rjsf-team/react-jsonschema-form) (rjsf) — авто-формы из JSON Schema
- Мета-таблица `entity_defs`: `{type: string, schema: JSON Schema draft-07, title: string}`
- Данные: таблица `entities`: `{id, type, data: JSON, created_at, updated_at}`

## 4. Архитектура

```
entity_defs (конфиг сущностей)  ──►  /api/v1/entity/{type}      (CRUD, валидация из схемы)
        │                              ▲
        │                              │
        ▼                              │
   /admin/schemas (редактор схем)      │
        │                              │
        ▼                              ▼
   UI: списки + rjsf-формы  ◄────  GET /api/v1/schemas/{type}
```

- Схема сущности = JSON Schema (properties, required, enums). Хранится в БД, редактируется через админку.
- Универсальный CRUD: один набор эндпоинтов на все типы; валидация тела — схемой из БД.
- UI: `GET /api/v1/schemas/{type}` → rjsf рендерит форму; список = таблица из полей схемы.

## 5. Функциональные требования

### 5.1 Мета-слой и универсальный CRUD (обязательно)
| # | Требование |
|---|---|
| F1 | `GET /api/v1/schemas` — список схем; `GET/PUT /api/v1/schemas/{type}` — чтение/обновление схемы (обновление = замена JSON Schema) |
| F2 | PUT схемы валидирует сам JSON Schema (кривая схема → 422) |
| F3 | `POST/GET/PUT/DELETE /api/v1/entity/{type}` — CRUD любой сущности; тело валидируется схемой типа; unknown type → 404 |
| F4 | Отсутствие required-поля или нарушение enum → 422 с указанием поля (detail от JSON Schema validator) |
| F5 | Стартовые схемы (из `test_data/entity_schemas.json`): `partner`, `service`, `signature`, `qos_profile`, `duration` — покрывают сущности кейса |

### 5.2 Динамический UI (обязательно)
| # | Требование |
|---|---|
| F6 | Раздел на тип сущности: список записей (таблица) + форма создания/редактирования, сгенерированная rjsf из схемы |
| F7 | Изменение схемы (через админку) отражается в UI после обновления страницы **без пересборки и рестарта** |
| F8 | Валидация в форме совпадает с серверной (те же сообщения об ошибках) |

### 5.3 Демо «смена требований» (обязательно — это сердце демо)
| # | Требование |
|---|---|
| F9 | Страница `/admin/schemas`: выбор типа → textarea с JSON Schema → «Сохранить» → PUT |
| F10 | Экспорт-эндпоинт `GET /api/v1/export/{partner_id}` собирает партнёра с сервисами/сигнатурами/назначениями по **конфигу связей** (см. `test_data/relations.json`) — связи тоже конфиг, не код |

## 6. Сценарий демо (6 минут)

1. **«Первое демо» (2 мин):** открыть UI, показать CRUD сервиса и сигнатуры (как в обычном инвентори).
2. **«Заказчик меняет требования» (3 мин):** в `/admin/schemas` для `signature`:
   - добавить опциональное поле `ipv6` (string, format ipv6);
   - поле `uri` сделать необязательным (убрать из required);
   - для `service` добавить поле `sla_percent` (number, 99..99.999).
   - Сохранить каждую схему → вернуться в UI → **новые поля появились в формах, старые записи не сломались**.
3. **Проверка API (1 мин):** POST сигнатуры с `ipv6` и без `uri` → 201; POST сервиса с `sla_percent: 99.5` → 201, с `sla_percent: 50` → 422 (вне диапазона).
4. Вывод жюри: правка требований = правка JSON-схемы, минуты вместо цикла разработки.

## 7. Критерии приёмки — как мы поймём, что результат достигнут

> Проверка = выполнить действие и наблюдать результат. Главный принцип варианта: **ни одно изменение модели не требует правки кода или пересборки**.

| # | Как проверяем | Успех = |
|---|---|---|
| A1 | `POST /api/v1/entity/signature` с телом, нарушающим схему (нет `port`) | 422, в detail указано поле `port` |
| A2 | Изменить схему `signature` через `PUT /api/v1/schemas/signature` (добавить `ipv6`) → обновить страницу UI | Поле `ipv6` появилось в форме создания сигнатуры; рестарт/пересборка не выполнялись |
| A3 | Создать запись с `ipv6` до изменения схемы (шаг «до») и после | «До» — 422; «после» — 201. Обе записи видны в списке после смены схемы |
| A4 | Добавить **новую сущность** `monitoring` целиком через `/admin/schemas` (схема из `test_data/demo_change.json`) | Раздел «monitoring» появился в UI; CRUD работает; в коде проекта нет упоминания `monitoring` |
| A5 | Сделать `uri` необязательным в схеме → POST сигнатуры без `uri` | 201; форма больше не требует `uri` |
| A6 | `GET /api/v1/export/mts-link-1` после сида | Структура как в `test_data/expected_export.json`: партнёр → сервисы → сигнатуры → профили, связи из `relations.json` |
| A7 | Исторические данные: записи, созданные по старой схеме (с обязательным `uri`), после смены схемы | Читаются (GET) без ошибок; в таблице отображаются |
| A8 | Ввести в редактор схем невалидный JSON Schema (напр. `{"properties": "not-an-object"}`) | 422, старая схема не перезаписана |

**Демо считается успешным**, если A1–A8 выполнены, при этом ни один шаг не потребовал изменения исходного кода, пересборки фронтенда или перезапуска сервера (кроме обновления страницы браузера).

## 8. Тестовые данные (`test_data/`)

- `entity_schemas.json` — стартовые JSON Schema пяти сущностей кейса (partner, service, signature, qos_profile, duration).
- `relations.json` — конфиг связей для экспорта (service.partner_id → partner и т.д.).
- `seed_entities.json` — стартовые записи: партнёр mts-link-1, сервис, сигнатуры, профиль, назначение.
- `demo_change.json` — изменения для демо: новая схема `signature` (с ipv6, uri опционален), новая схема `service` (с sla_percent), новая сущность `monitoring`.
- `expected_export.json` — эталон экспорта после сида.

## 9. Рекомендуемый порядок вайбкодинга (3 часа)

1. **0:00–0:40** — мета-модель (`entity_defs`, `entities`), универсальный CRUD + валидация схемой (F1–F5).
2. **0:40–1:30** — rjsf-формы и списки из схем (F6–F8).
3. **1:30–2:00** — админка схем (F9) + редактор.
4. **2:00–2:30** — экспорт по конфигу связей (F10).
5. **2:30–2:50** — прогон A1–A8, особенно A4 (новая сущность).
6. **2:50–3:00** — репетиция сценария «смена требований».
