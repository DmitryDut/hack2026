# ТЗ. Вариант 4 — Симулятор песочницы + старт эксплуатации

**Хакатон по вайбкодингу, 3 часа. Самодостаточный документ: можно копировать целиком в ИИ-ассистент.**

---

## 1. Что строим

Прототип шагов 4–5 кейса: **тестирование конфигурации партнёра в «песочнице»** (чистая эмуляция с полным контролем за изменениями) и **переход к коммерческому старту** через замоканный GSMA QoD APIgw. Ядро — конечный автомат статусов конфигурации `Draft → InTesting → Passed/Failed → Applied`, построчный проход по сигнатурам с ручным подтверждением, контроль изменений и журнал событий.

Данные предзаполнены сидом — на демо не тратим время на ввод.

## 2. Контекст кейса (для ИИ-ассистента)

QoD management после конфигурирования сервисов партнёра предлагает тестирование в песочнице: построчный проход по всем зафиксированным сигнатурам с назначенным QoS-профилем и Duration, ручное подтверждение корректности. Песочница — эмуляция, демонстрирующая логику для партнёра и оператора: полный контроль за изменениями (любая правка сбрасывает прогон), ограничение ответственности (только ресурсы партнёра). После успешного теста — старт коммерческого использования через вызов GSMA QoD APIgw; при провале — возврат на конфигурирование. Гипотеза из материалов: политики до переноса в статусе Draft, после — Applied.

## 3. Стек (фиксированный)

- **Backend:** Python 3.11+, FastAPI, SQLite (`sandbox.db`)
- **Frontend:** React 18 + Vite: степпер статусов + таблица сигнатур + журнал
- **Мок GSMA QoD APIgw:** отдельные эндпоинты в том же приложении (префикс `/mock-gsma/`), имитация задержки 300–800 мс

## 4. Модель данных и автомат состояний

```
Partner, Service, Signature, QoSProfile, Duration — как в варианте 1 (сид уже заполнен)

TestRun:  id, service_id, status enum(draft, in_testing, passed, failed, applied),
          started_at, finished_at
TestStep: id, test_run_id, signature_id, result enum(pending, success, error),
          confirmed_by_user bool, checked_at, error_message
EventLog: id, entity_type, entity_id, event, details, created_at
```

**Автомат конфигурации сервиса:**
```
Draft ──start──► InTesting ──все шаги success+confirmed──► Passed ──apply──► Applied
  ▲                  │
  └──reset───────────┴──любой шаг error──► Failed
  ▲
  └──любое изменение сигнатуры/профиля в статусах InTesting/Passed/Failed──► Draft (прогон сброшен)
```

Правила:
- Изменение сигнатуры/назначения пока статус ≠ Draft/Applied → переход в Draft, прогресс теста теряется, событие в журнал.
- Apply возможен только из Passed.
- В Applied изменения запрещены (нужен сброс в Draft с подтверждением оператора — событие в журнал).

## 5. Функциональные требования

| # | Требование |
|---|---|
| F1 | Страница сервиса: степпер статусов (Draft → InTesting → Passed → Applied), текущий статус подсвечен |
| F2 | Кнопка «Начать тест»: создаёт TestRun + TestStep на каждую сигнатуру сервиса (построчный проход), статус → InTesting |
| F3 | Таблица шагов: сигнатура, QoS-профиль, Duration, результат (pending/success/error), галка «подтверждаю», кнопка «Проверить» на строку |
| F4 | «Проверить» → запрос к `/mock-gsma/validate` → результат success или error (сценарий задаётся сидом: какая сигнатура падает — см. `test_data/demo_scenario.json`) |
| F5 | Любой error → статус TestRun = Failed; UI показывает кнопку «Вернуться к конфигурированию» → Draft |
| F6 | Все success + все confirmed → Passed |
| F7 | В InTesting/Passed/Failed изменение сигнатуры или назначения → автоматический сброс в Draft + запись в EventLog «прогон сброшен из-за изменения» |
| F8 | Кнопка «Старт коммерческой эксплуатации» (доступна в Passed) → `POST /mock-gsma/qod/sessions` с телом {partner_id, service, qos_profile, duration, signatures} → ответ `session_id` → статус Applied, session_id сохранён |
| F9 | Журнал событий (панель): все переходы статусов, проверки, изменения, apply — с timestamp |
| F10 | Видны только партнёрские ресурсы: в списке сервисов фильтр по partner_id из мока авторизации (`X-Partner-Id` заголовок) |

## 6. Сценарий демо (5 минут, по `test_data/demo_scenario.json`)

1. Открыть сервис «Link ВКС» (сид): статус Draft, 4 сигнатуры, профиль Platinum/12H.
2. «Начать тест» → InTesting → таблица шагов.
3. «Проверить» по строкам: 3 сигнатуры success (подтвердить галками), 4-я (`media2`, порт 5005) — error «RTP-поток не отвечает» → Failed.
4. Показать контроль изменений: попытаться отредактировать сигнатуру → прогон сброшен в Draft, событие в журнале.
5. Исправить `media2` (порт 5006) → новый прогон → все success → подтвердить → Passed.
6. «Старт коммерческой эксплуатации» → мок APIgw → session_id → Applied. Показать журнал целиком.

## 7. Критерии приёмки — как мы поймём, что результат достигнут

> Проверка = выполнить цепочку действий из демо-сценария и наблюдать переходы. Автомат должен вести себя детерминированно: недостижимые статусы недоступны, изменения сбрасывают прогон.

| # | Как проверяем | Успех = |
|---|---|---|
| A1 | «Начать тест» на сервисе в Draft | TestRun создан, по одной TestStep на каждую сигнатуру (4 шт из сида), статус InTesting |
| A2 | Проверить все строки, где 4-я настроена падать (`demo_scenario.json`) | Первые 3 — success; 4-я — error с сообщением; статус Failed; кнопка возврата в Draft видна |
| A3 | В Failed нажать «Вернуться к конфигурированию» | Статус Draft; новый прогон стартует заново |
| A4 | В InTesting изменить любую сигнатуру (через UI/API) | Статус сброшен в Draft; в EventLog запись о сбросе; TestStep-и старого прогона не переносятся |
| A5 | Пройти успешно все шаги + подтвердить все галки | Статус Passed |
| A6 | В Passed нажать «Старт эксплуатации» | Запрос к `/mock-gsma/qod/sessions` зарегистрирован; получен session_id; статус Applied; session_id виден в UI |
| A7 | В Applied попытаться изменить сигнатуру | Изменение отклонено или требует явного сброса; в EventLog есть след попытки |
| A8 | Открыть журнал событий | Видны все переходы: start, каждый check, failed, reset, passed, apply — с timestamp по возрастанию |
| A9 | Запросить сервисы с заголовком `X-Partner-Id: other-partner` | Сервисы mts-link-1 не видны (изоляция ресурсов) |

**Демо считается успешным**, если A1–A9 выполнены подряд за ≤5 минут без правок кода и перезапуска.

## 8. Тестовые данные (`test_data/`)

- `seed.json` — партнёр, 2 сервиса, 4 сигнатуры (в т.ч. `media2` для провала), профили, назначение Platinum/12H.
- `demo_scenario.json` — какой шаг падает, с каким сообщением; ожидаемая последовательность событий.
- `mock_apigw_contract.json` — контракт мока: запрос/ответ `/mock-gsma/qod/sessions` и `/mock-gsma/validate`.
- `expected_event_log.json` — эталон журнала после полного прогона демо.
